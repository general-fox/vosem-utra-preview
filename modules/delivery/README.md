# Отложенный модуль доставки

По умолчанию `npm run dev`, `npm run build`, `npm run build:reg` и
`npm run build:reg:test` запускают/собирают сайт-каталог с ручным меню.

Исходники доставки сохранены на прежних путях, чтобы не ломать импорты и
сохранённые ссылки. Граница модуля задаётся профилем сборки, а не удалением кода.

- Клиент: `cart*`, `dish-cart.js`, `checkout*`, `order-client.js`, `order-terms.html`,
  `kds-status.js`, `staff*` в корне проекта.
- Сервер: `hosting/php/orders.php`, `kds-*`, `staff-*`, `telegram*`, импорт меню;
  задания `hosting/kds-worker.php` и `hosting/telegram-worker.php`.
- Данные: закрытые `orders-data`, `kds-data`, конфигурации КДС/заказов/Telegram.
  Их не удаляют и не включают в обычные архивы исходников.
- Тесты: существующие suites заказов, Telegram, staff, KDS, корзины и checkout.

В каталоге отсутствуют страницы и клиентские ресурсы этих модулей. Серверный
`app/features.php` отключает обработчики даже при наличии старого кода и секретов.
Пакет обновления подменяет старые cron-точки входа заглушками. Регистрация клуба
гостей не относится к доставке и продолжает работать независимо.

Для дальнейшей разработки модуля существуют явные команды:

```text
npm run dev:delivery
npm run build:reg:test:delivery
npm run build:reg:delivery
```

Они пересобирают соответствующий выходной каталог с доставкой. Перед возвратом
на хостинг нужно заново проверить меню и соответствия блюд, оплату, HTTPS API,
конфигурацию объекта и фоновые задания; затем обновить полный пакет, включая
`features.php`. Старые секреты и данные не меняются автоматически. Рабочая
оплата и отправка заказа не включаются одной командой сборки.

Проверка каталога: сборки `build:reg`, `build:reg:test`, затем `test:catalog`.
Для старых HTTP-тестов доставки сначала соберите соответствующий delivery-профиль.
