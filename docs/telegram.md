# Бот и приложение сотрудников

Бот: [@vosem_utra_bot](https://t.me/vosem_utra_bot).
Интерфейс — `staff.html`, отдельная демонстрация — `staff-demo.html`.
Демонстрация использует вымышленные данные в памяти страницы и не обращается
к рабочим заказам. Само открытие `staff.html` в обычном браузере не даёт доступа.

## Куда вставить токен

На компьютере подготовлен приватный файл
`C:\8utra\vosem-utra-preview\.data\telegram-config.php`. Вставить токен BotFather
между кавычками в строке `'botToken' => ''`. Пока оставить `'enabled' => false`.
Файл и вся `.data` исключены из Git. Не вставлять токен в HTML, JavaScript,
Vite-переменные, переписку, публичный репозиторий или URL в адресной строке.

После размещения приватный файл должен находиться рядом с `admin-config.php`:
`vosem-utra-private/telegram-config.php`, вне публичной папки домена. Сборка
содержит только `telegram-config.example.php`, с пустыми значениями.
Обновление кода не перезаписывает рабочие конфиги и базу.

`webhookSecret` — отдельный случайный ключ входящих запросов Telegram, не токен
бота. В локальном приватном файле он уже создан. Токен бота используется только
PHP на сервере. Ни ответы API, ни приложение сотрудников его не получают.

## Первое подключение

1. Согласовать отдельный HTTPS-адрес для проверки. Опубликовать PHP-комплект
   на REG.RU с отдельной приватной папкой и SQLite. GitHub Pages показывает
   интерфейс, но не выполняет PHP, не принимает Telegram webhook и не хранит заказы.
2. Проверить PHP 8.3+, PDO SQLite, cURL с проверкой сертификатов и исходящий HTTPS
   к `api.telegram.org`; настроить cron раз в минуту. На хостинге не нужен
   постоянно запущенный Node.js или компьютер с открытой командной строкой.
3. Заполнить в приватном конфиге токен, `botUsername`, `webhookSecret`,
   `webAppUrl` (точный HTTPS-адрес `staff.html`) и контакт ответственного.
   Базовый вариант уведомлений — `notifications.mode = private`.
   После заполнения включить `enabled`; до публикации оставить выключенным.
   Для HTTPS-стенда в `admin-config.php` задать `'orders_environment' => 'staging'`,
   в Telegram-конфиге — `'environment' => 'staging'`. Для рабочего сайта оба
   значения — `production` (это значение среды заказов по умолчанию).
   Несовпадение сред закрывает вход и отправку уведомлений. Базы и боты должны
   быть разными: смена флага не заменяет физическое разделение рабочих данных.
4. После публикации настроить webhook и кнопку приложения. Для разработчика
   подготовлен одноразовый CLI-инструмент `telegram-setup.php`: без `--apply`
   он показывает безопасный план, с `--apply` применяет настройки Telegram.
   Запускать только после проверки адреса; в аргументах передаётся путь к
   приватной папке, а не сам токен. Обычный вход сотрудников команд не требует.
5. Отправить боту `/id` в личном чате. Он покажет только Telegram ID отправителя.
   Передать ID администратору; тот добавляет `{id, name, role, active}` в `staff`
   приватного конфига. Роли: `employee` или `manager`. Username не даёт допуск.
   Первым руководителем предполагается `@boo_katan`; числовой ID ещё нужен.
6. Каждый допущенный сотрудник один раз отправляет `/start`, затем открывает
   приложение через `/orders` или кнопку уведомления. `/help` содержит подсказки.
7. Проверить полный сценарий на HTTPS, затем отдельно на Telegram Android,
   iPhone и компьютере. Зафиксировать URL и конкретный commit SHA.

Пример серверного расписания (пути заменить на реальные из панели хостинга):

```text
* * * * * /path/to/php /private/path/telegram-worker.php --private-dir=/private/path
```

Это серверная задача в панели REG.RU, а не команда, которую сотрудник запускает
при каждом входе. Worker обрабатывает Telegram; отправка интегратору r_keeper
пока не подключена. Не помещать worker/setup или конфиг в публичную папку.
Ответ на команды и уведомления поступает после ближайшего запуска cron,
обычно в пределах минуты. Контролировать успешное выполнение cron в панели.

Для общей группы задать `notifications.mode = group`, фиксированный `groupChatId`
и при необходимости `miniAppName`. В группе используется URL на Main Mini App
или именованное приложение с `startapp`, а не личная кнопка `web_app`.
Main Mini App/short name должны быть настроены через BotFather. Групповые
сводки не содержат телефон, адрес и комментарии гостя. Группа не заменяет допуск.
Проверить групповой режим отдельно, прежде чем включать его для персонала.

## Вход и права

PHP проверяет HMAC исходной строки `Telegram.WebApp.initData` по официальному
[алгоритму Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).
Окно запуска — 5 минут, допуск будущего времени — 30 секунд. Числовой ID берётся
из подписанных данных, затем сверяется с активным списком сотрудников.

Сессия действует до 2 часов. В браузере непрозрачный Bearer-токен хранится только
в памяти, на сервере — его хеш. Каждый API-запрос заново проверяет действующий
допуск. Изменение `active` на `false` закрывает новые запросы и новые уведомления.
Уже отправленные ранее сообщения в Telegram автоматически не стираются.

Обычный сотрудник редактирует и принимает только назначенный ему заказ.
Руководитель явно переназначает его с причиной; просмотр чужой карточки
не меняет ответственного. Эти проверки выполняются сервером.
Редактор меню и его MFA остаются отдельным административным контуром.

API использует тот же origin, что приложение. Отдельный API для Pages потребует
отдельного согласования CORS/CSP и проверки; такого развёртывания сейчас нет.
Только `staff.html` разрешено открывать во фрейме официального Telegram Web;
административная панель сохраняет защиту от встраивания.
На Apache правило различает страницы по исходной строке запроса
([THE_REQUEST](https://httpd.apache.org/docs/2.4/mod/mod_rewrite.html#rewritecond)),
чтобы внутренний переход к `app.php` не восстановил запрет встраивания Mini App.
На HTTPS-стенде проверить фактические заголовки и ссылку с `?order=…`: локальный
PHP-сервер не исполняет `.htaccess` и не проверяет конфигурацию панели REG.RU.

## Работа с заказом

«Взять в работу» назначает одного сотрудника атомарно. Каждое изменение
проверяет `expectedVersion`; конфликт не затирает сохранённую работу другого.
Список обновляется каждые 15 секунд только на активном экране. Несохранённая
форма не подменяется автоматически новой версией с сервера.

Цены берутся из текущего меню. Изменение цены требует явного повторного
согласования. Принятие требует конкретного согласованного времени, непустого
доступного состава, корректных контактов/адреса, известной доставки, сохранённых
правок и отметки о согласовании с гостем.

Сохранение, недозвон и отмена не создают `order.accepted`. При принятии статус,
окончательный снимок, история и единственное событие фиксируются в одной
транзакции. Повторы используют прежний ключ. Принятый заказ доступен только
для просмотра; изменение или отмена согласуются с ответственным за кассу.

Служебная заметка отделена от комментария для выполнения и не включается в
событие интегратора. Снимок первичной заявки не переписывается. Новые номера
заказов последовательны; старые номера остаются прежними. Внутренний ID случаен.

## Уведомления и интеграция

Входящий Telegram webhook проверяет отдельный secret header и сохраняет update
до ответа. Повтор того же update не создаёт повторную команду. Cron отправляет
уведомления и обновляет сохранённые `chat_id/message_id` по актуальной базе.
Ошибка Telegram не откатывает заказ. Неудачи доступны руководителю в приложении,
а не только в самом Telegram. Сообщения могут повториться при неопределённом
ответе `sendMessage`: Telegram не предоставляет ключ идемпотентности этого метода;
повторное уведомление всегда ведёт на тот же заказ.

Рабочий отправитель событий интегратору будет реализован по следующему ТЗ.
Сейчас событие принятия хранится в `waiting_configuration`; интерфейс сообщает,
что интеграция ожидает подключения. Нет утверждения, что заказ появился в кассе.
Перед подключением согласовать JSON Schema, включая `address.streetHouse`:
сайт собирает улицу и дом одним полем, автоматически угадывать их разделение нельзя.

Базу, конфиги и резервные копии хранить вне публичной папки и Git. Тестовую и
рабочую среды изолировать: разные базы, боты и ключи. Сроки хранения и резервные
копии согласовать перед рабочим запуском. Локальные тесты используют фикстуры и
подменённый транспорт: они не отправляют сообщений созданному пользователем боту.

Для просмотра на компьютере открыть `/staff-demo.html`. Локальный Vite сохраняет
гостевые тестовые заявки через PHP, но рабочий контур сотрудников проверяется
на собранном PHP-сайте: блокировка каталога должна быть общей для админки и
принимающего заказ сотрудника. Мост к локальному Node-каталогу не разрешает
сохранение и принятие настоящих заказов. В приложении нет обхода Telegram-входа
через query-параметр или демонстрационный аккаунт.
