# ТЗ: сайт, корзина и оформление доставки

Версия 1.0 от 28.09.2026. Рабочее задание для последующей реализации.
Создание этого документа не означает, что описанные функции уже реализованы.

Связанные документы: [бот и Web App сотрудников](delivery-staff-spec.md),
[сервер и исходящий вебхук](delivery-webhook-spec.md).

## 1. Задача и границы первой версии

Гость выбирает блюда из существующего меню сайта «Восемь утра», собирает
корзину и отправляет заявку на доставку или самовывоз. Сотрудник получает
уведомление в Telegram, звонит гостю, уточняет данные и состав в Web App,
затем принимает заказ. При принятии сервер сохраняет окончательный заказ
и создаёт событие для отправки интегратору r_keeper.

В первую версию входят:

- Корзина, оформление, серверная проверка заказа и экран результата.
- Доставка и самовывоз; ближайшее время или заказ к определённому времени.
- Telegram-бот для сотрудников, список заказов и редактирование до принятия.
- История изменений, распределение заказов между сотрудниками.
- Надёжная отправка вебхука и защищённый тестовый приёмник.
- Публичный репозиторий, публикация тестового окружения через GitHub и проверки на HTTPS.

В отдельные этапы вынесены банк и онлайн-оплата, фактическое создание заказа
в r_keeper, курьерское приложение, отслеживание курьера, бонусы, промокоды,
автоматические SMS гостю и обработка заказа кухней. Интегратор r_keeper
получает наш контракт вебхука; адаптер к кассовой системе реализует он.

## 2. Что уже есть в проекте

Основание — локальная рабочая версия `vosem-utra-preview`, проверенная
28.09.2026, и её remote `https://github.com/general-fox/vosem-utra-preview`.
Это описание файлов проекта, а не подтверждение состояния опубликованного сайта.

| Актуальное меню | `GET /api/menu`; сохранённое меню имеет приоритет над начальным JSON | Сайт и Web App используют один серверный источник |
| Управление меню | Существующая административная панель | Продолжить редактирование через неё |

| Публикация | Vite; статическая демонстрация; PHP-сборка для REG.RU | Расширить существующую сборку |

через административную панель нельзя перезаписывать очередной публикацией.

## 3. Общая схема и тестовое окружение

Поток: сайт → API и база заказов → уведомление Telegram → Web App сотрудника
→ принятие на API → очередь исходящих событий → приёмник интегратора → r_keeper.

Публичный репозиторий хранит исходники и обезличенные примеры. Интерфейсы
получают публичные HTTPS-адреса. Telegram требует HTTPS для обычного запуска
Web App; публичность репозитория сама по себе не является требованием Telegram.
Источник: [Telegram WebAppInfo](https://core.telegram.org/bots/api#webappinfo).

GitHub Pages обслуживает статические файлы и не выполняет PHP/API.
Поэтому одного репозитория и Pages недостаточно для хранения заказов,
работы бота и отправки вебхуков. Источник:
[назначение GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages).

Принять следующую схему:

- GitHub Actions запускает автоматические проверки и собирает проект.
- GitHub Pages используется для демонстрации интерфейсов с вымышленными данными.
- Полный сценарий проверяется на отдельном опубликованном HTTPS-стенде
  с PHP API, базой данных, тестовым ботом и тестовым приёмником вебхука.
- Предпочтительно сайт и Web App на полном стенде размещать рядом с API на
  одном origin. При проверке интерфейса Pages с тестовым API использовать
  явный `API_BASE_URL` и ограниченный CORS.
- Рабочие коммерческие заказы идут через основной HTTPS-хостинг сайта.
  GitHub Pages не выбирать хостингом рабочей системы заказов:
  [ограничения сервиса](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits).
- Приёмочные проверки Telegram выполняются внутри настоящего Telegram
  на опубликованных адресах. Localhost не считается приёмочным окружением.

Точные адреса стенда и способ доступа к хостингу определяются перед развёртыванием.
Не выдавать существующий публичный репозиторий за уже работающий backend.
В тестовом окружении использовать только вымышленные телефон, адрес и заказы;
оно не должно вызывать рабочий r_keeper, банк или рабочий бот.

## 4. Меню и доступность блюд

Сайт и приложение сотрудников получают один и тот же актуальный каталог.
Идентификатор блюда остаётся стабильным после изменения названия или цены.

Добавить признак `availableForOrder`, отдельный от `published`:

- `published=false`: позиция скрыта из публичного меню и недоступна для новых заказов.
- `published=true, availableForOrder=false`: позиция видна с пометкой
  «Временно недоступно», добавление отключено.
- Оба значения `true`: блюдо можно заказать и добавить сотрудником в заказ.

Начальное значение нового признака для существующего каталога — `true`;
действительная доступность всегда требует также `published=true`.
Управление признаком добавить в существующую панель меню. Обновить её сохранение,
PHP- и Node-валидаторы, экспорт и начальные данные, чтобы поле не терялось.

Публичный ответ меню дополнить `revision` без удаления существующих полей.
Пути фотографий должны корректно работать и из подпапки Pages, и при отдельном API.
Статический JSON разрешён для демонстрации меню. При недоступном API заказов
нельзя имитировать успешную отправку или использовать старые цены как подтверждённые.

Пользовательские добавки и варианты блюд не придумывать. Если фактическое меню
потребует выбора варианта, сначала определить отдельные продаваемые позиции
или согласовать модель модификаторов с интегратором.

## 5. Корзина

- Кнопка «В корзину» в каждой доступной карточке, включая карточки без фото.
- Повторное добавление того же блюда увеличивает количество.
- Кнопки изменения количества и удаления; название, цена, количество и сумма строки.
- Видимый вход в корзину с количеством порций и суммой блюд.
- Пустая корзина содержит ссылку в меню; переход к оформлению отключён.
- Корзина с ID блюд и количествами сохраняется между обновлениями страницы.
  Телефон и адрес не сохранять вместе с ней в `localStorage`.
- При открытии корзины сверять цены и доступность с сервером.
- Изменение цены показывать явно. Недоступное блюдо отмечать и предлагать удалить;
  самостоятельно заменять его другим блюдом нельзя.
- Технические лимиты первой версии: до 50 разных строк, от 1 до 99 порций
  одной позиции. Это настраиваемые ограничения, а не согласованный лимит кафе.

Кнопка перехода: «Оформить заказ».

## 6. Оформление заказа

Оформление — отдельная страница `checkout.html` в стиле существующего сайта,
адаптированная прежде всего под телефон. Регистрация и Telegram гостю не нужны.

| Поле | Обязательность | Правило |
| --- | --- | --- |
| Получение | Всегда | «Самовывоз» / «Доставка»; требуется осознанный выбор |
| Телефон | Всегда | Понятная маска, серверная нормализация, сохранение в международном формате |
| Имя | Нет | Не препятствует оформлению |
| Город/населённый пункт | Для доставки | Может подставляться из настроек кафе, но должен быть явно указан |
| Улица и дом/строение | Для доставки | Заполнены; для нестандартного адреса допустима согласованная текстовая форма |
| Квартира/офис | Нет | Частный дом не требует квартиры |
| Подъезд, этаж, домофон | Нет | Дополнительные поля |
| Указания курьеру | Нет | Отдельно от пожеланий к блюдам |
| Время | Всегда | «Как можно скорее» по умолчанию либо «К определённому времени» |
| Дата и время | Для заказа ко времени | Оба обязательны |
| Комментарий к заказу | Нет | До 1000 символов |
| Подтверждение условий обработки данных | По согласованному тексту | Ссылка на документы именно для заказа |

Телефон не является подтверждённым номером до разговора с гостем;
SMS-проверка в первую версию не входит. Точный перечень принимаемых кодов стран
согласуется перед запуском; исходное предположение — российские номера.

Для самовывоза поля доставки скрываются; сервер получает `address=null` и
стоимость доставки 0. Показать адрес кафе из настроек и согласованное время выдачи.
При переключении способов получения сервер заново рассчитывает условия.

Когда выбрано ближайшее время, `requestedAt=null`; пустые дата и время не
превращаются в полночь. Если выбран заказ ко времени, отсутствие даты — ошибка,
а не автоматическое переключение в ближайшее время.

Для доставки время означает желаемое прибытие к гостю, для самовывоза — выдачу
в кафе. Показать пояснение, что точное время подтвердит сотрудник по телефону.

## 7. Дата, время, территория и стоимость

Настройки заведения должны хранить часовой пояс, часы приёма заказов,
доставки и самовывоза, нерабочие даты, минимальное время подготовки,
шаг слотов и максимальную глубину предзаказа. Исходное техническое предположение
о часовом поясе — `Europe/Moscow`; подтвердить его перед запуском.

Доступность времени проверяется и в браузере, и сервером. Запретить прошлое
время, слишком ранний слот и время вне расписания. Вне рабочих часов
не обещать доставку «сейчас»: предложить допустимое время, если разрешён предзаказ.

Зона доставки, тариф, минимальная сумма и порог бесплатной доставки
задаются настройками после ответа заказчика. Не выдумывать расстояния,
тарифы или срок доставки. До автоматизации проверки территории сотрудник
подтверждает адрес вручную, а сайт явно пишет об этом.

Если заказчик допускает расчёт доставки при звонке, сайт показывает
«Блюда: …; доставка и окончательная сумма — после подтверждения».
Неизвестная стоимость хранится как `null`, а не как бесплатная доставка.
Принять такой заказ можно только после указания точной стоимости и согласования
полной суммы. Для рабочего запуска этот режим должен быть выбран явно.

## 8. Проверка суммы и отправка

Цены и суммы определяет сервер по ID блюд. Денежные суммы заказов хранятся
целыми числами в копейках, валюта — RUB. Поле `price` действующего меню
остаётся в рублях для совместимости; преобразование выполняется сервером.

Перед отправкой получить серверный расчёт с `quoteId`, версией меню,
составом, стоимостью блюд, доставки и итогом. Срок действия расчёта —
5 минут как начальное техническое значение. Если изменились цена, состав,
адрес или время, расчёт обновляется и изменения показываются гостю.

В запросе создания заказа передавать расчёт, данные получения, контакты
и ключ идемпотентности. Цены из браузера не считать доверенными.
На сервере повторно проверить каталог, доступность, время и действительность расчёта.
При расхождении вернуть актуальные данные и попросить гостя повторить отправку
после просмотра изменений; не менять сумму незаметно.

Кнопка: «Отправить заказ». Во время запроса она блокируется.
Повтор одного запроса после тайм-аута возвращает тот же заказ;
повторное нажатие не создаёт новый. Один ключ с изменённым телом запроса
возвращает конфликт, а не перезаписывает старый заказ.

При ошибке корзина и введённые поля остаются на экране. Корзина очищается
только после подтверждения сервером, что заказ сохранён. Тайм-аут не считается
доказательством, что сохранения не было: сначала повторить запрос с прежним ключом.

## 9. Экран результата и связь с гостем

После успешного сохранения показать номер заказа, краткий состав, сумму
или её предварительный характер, получение и желаемое время.

Текст: «Заказ №… получен. Сотрудник позвонит, чтобы подтвердить состав,
сумму и время». Статус — «Ожидает подтверждения».

Не показывать «Заказ принят» до действия сотрудника. Кнопка возврата в меню
и телефон кафе доступны на экране результата.

Гость не обязан открывать бота. Подтверждение в первой версии происходит
звонком. Личный кабинет, общедоступный поиск по номеру заказа и постоянная
страница отслеживания не входят в объём. Если экран результата восстанавливается
после обновления, использовать только непредсказуемый ограниченный токен,
а не доступ по последовательному номеру.

## 10. Оплата — последующий этап

Способ оплаты и банк пока не определены. Не показывать выдуманный выбор
наличных, карты, СБП или эквайринга. Не запрашивать данные банковской карты.
Текст об оплате перед рабочим запуском согласуется с заказчиком.

В модели уже предусмотреть независимые поля `payment.method=null`,
`payment.status="not_configured"`, `payment.paidAmountMinor=null`.
«Принят» никогда автоматически не означает «Оплачен».

Позже отдельное ТЗ определит банк, момент оплаты относительно согласования,
изменение суммы после редактирования, возвраты и подтверждение платежа.
Подключение банка не должно требовать переписывать корзину и модель заказа.

## 11. Общие статусы и история

| Код | Смысл | Доступные переходы |
| --- | --- | --- |
| `new` | Заявка сохранена, сотрудник не назначен | `processing`, `cancelled` |
| `processing` | Сотрудник согласовывает заказ | `accepted`, `cancelled`; возврат в `new` при освобождении |
| `accepted` | Согласованы состав, получение, время и сумма | В первой версии карточка только для просмотра |
| `cancelled` | Отменён до принятия, указана причина | Терминальный статус |

«Не дозвонились» — отметка о контакте, заказ остаётся на согласовании.
Автоматической отмены и автоматического принятия нет.

Сохранить исходную заявку, каждое сохранённое изменение с автором и временем,
а также окончательный снимок при принятии. Изменение меню не должно менять
историю или уже согласованные суммы заказов.

Статус заказа, доставки вебхука и платежа — разные поля. Подробные правила
согласования и редактирования находятся в ТЗ сотрудников.

## 12. Проверки сайта и критерии приёмки

Проверки фиксируются для конкретного commit SHA в GitHub и опубликованного
тестового адреса. Автоматические проверки запускаются в GitHub Actions;
полный пользовательский сценарий проверяется на HTTPS-стенде.

1. Состав, фотографии, категории и цены соответствуют существующему меню.
2. Изменение меню в панели отражается на сайте и в Web App без повторного ввода.
3. Корзина работает на мобильном и компьютере, сохраняет количество после обновления.
4. Самовывоз не требует адреса; доставка требует адрес и телефон.
5. Ближайшее время работает без даты; заказ ко времени требует оба поля.
6. Прошедшие, закрытые и слишком ранние слоты отклоняются сервером.
7. Подмена цены в запросе не меняет серверную сумму.
8. Изменившаяся цена и недоступное блюдо показываются гостю до отправки.
9. Неизвестная стоимость доставки не отображается как ноль.
10. Двойное нажатие и повтор запроса после потери ответа создают один заказ.
11. Сбой API сохраняет корзину и форму; успешный экран появляется только после записи.
12. Сохранённый заказ попадает в список сотрудников даже при временном сбое Telegram.
13. На узком экране нет горизонтальной прокрутки; поля, ошибки и кнопки доступны с клавиатуры.
14. Нет оплаты, ложного статуса оплаты, реальных персональных данных или секретов в сборке.

## 13. Порядок реализации и нерешённые условия

1. Утвердить контракт данных из трёх ТЗ; подготовить тестовый HTTPS-стенд,
   базу, тестового бота и настройки GitHub Actions.
2. Подключить общий каталог и серверный расчёт; реализовать корзину и оформление.
3. Реализовать хранение заказа, уведомления, Web App и историю изменений.
4. Реализовать принятие с атомарным созданием события, отправитель и приёмник вебхука.
5. Проверить весь маршрут, ошибки, параллельную работу и повторную доставку.
6. Передать интегратору контракт и тестовые примеры. Позже подключить r_keeper и банк.

До рабочего запуска получить от заказчика: территорию и тарифы доставки,
минимальную сумму, расписание, сроки подготовки, допустимый предзаказ,
адрес самовывоза, правила недозвона, список сотрудников, способ получения
уведомлений, тексты условий оформления и способ оплаты. Отдельно определить
процесс изменения/отмены уже принятого заказа вместе с интегратором.

Эти неизвестные параметры не мешают реализации на настраиваемых тестовых
значениях. Тестовые предположения нельзя выдавать за условия кафе.
