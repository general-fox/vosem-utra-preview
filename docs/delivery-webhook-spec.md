# ТЗ: сервер заказов и вебхук для интеграции с r_keeper

Версия 1.0 от 28.09.2026. Предлагаемый контракт нашей системы.
Формат не является официальным API r_keeper и должен быть согласован
с разработчиком принимающей интеграции до рабочего подключения.

Связанные документы: [сайт и оформление](delivery-site-spec.md),
[бот и Web App сотрудников](delivery-staff-spec.md).

## 1. Ответственность компонентов

Web App отправляет команду принятия нашему серверу. Сервер проверяет
сотрудника и заказ, сохраняет принятие и создаёт исходящее событие.
Фоновый отправитель доставляет JSON на HTTPS-адрес интегратора.
Интегратор сопоставляет блюда, создаёт заказ в r_keeper и обеспечивает
защиту от повторного создания на своей стороне.

Браузер сотрудника не отправляет вебхук напрямую. В нём нет токена бота,
ключа подписи, доступа к базе или реквизитов r_keeper.

В проекте есть два независимых webhook-направления:

- Входящий webhook Telegram → наш API: команды и обновления бота.
- Исходящий webhook нашего API → интегратор: событие `order.accepted`.

Название «вебхук» не означает файл для ручного скачивания. Это сохранённое
событие и HTTPS POST с его данными. До подключения реального адреса
использовать защищённый тестовый приёмник и журнал доставки.

## 2. Техническая основа

Рабочее предположение с учётом проекта: PHP 8.3+ на существующем типе хостинга,
SQL-база с транзакциями, например MySQL/MariaDB с InnoDB, и серверный cron.
До реализации инфраструктуры проверить наличие PDO, базы, исходящего HTTPS
и cron с периодом не более минуты. Если возможностей нет, выбрать отдельный
сервер API, сохранив контракт и существующий фронтенд.

GitHub Actions используется для проверки и публикации, а не как постоянно
работающий бот или очередь. Рабочие заказы, сессии и очередь не хранить
в JSON-файлах публичного репозитория или памяти процесса.

Каталог остаётся единым с существующей административной панелью.
Не обязательно переносить его в SQL в первой версии: использовать серверный
адаптер к текущему хранилищу меню, возвращающий снимок и `revision`.
Проверку актуальности каталога и фиксацию принятия согласовать блокировкой
чтения/изменения меню, общей с редактором, чтобы цена не менялась между
проверкой и сохранением принятого снимка. Долгие сетевые вызовы под этой
блокировкой запрещены; порядок блокировок всегда одинаковый.

## 3. Данные и инварианты

Минимальные сущности:

| Сущность | Данные |
| --- | --- |
| `orders` | UUID, номер, среда, статус, версия, получение, контакты, адрес, желаемое/согласованное время, суммы, ответственный, даты |
| `order_items` | ID строки, стабильный ID блюда, снимок названия, количество, цена и сумма в копейках |
| `order_revisions` | Исходный и последующие снимки/изменения, автор, действие, время, причина |
| `order_quotes` | Расчёт сервера, версия меню, состав, условия, время истечения |
| `staff` / настройки допуска | Telegram ID, служебное имя, роль, активность |
| `staff_sessions` | Хеш сессионного токена, сотрудник, срок действия |
| `idempotency_keys` | Область действия, ключ, хеш запроса, сохранённый результат |
| `integration_events` | ID события, тип, версия схемы, заказ, версия заказа, неизменяемое тело, состояние отправки |
| `webhook_attempts` | Событие, номер попытки, даты, HTTP-статус, краткая ошибка, следующий повтор |
| `telegram_notifications` | Заказ, назначение чата, message ID, состояние синхронизации |
| `telegram_updates` | Обработанные `update_id` для защиты от повторов Telegram |

Все суммы целые в минимальных единицах валюты. `subtotalMinor` равен сумме
строк, `totalMinor` равен `subtotalMinor + deliveryFeeMinor`.
До выяснения доставки два последних поля могут быть `null` по правилам сайта;
в событии принятия они уже обязательно определены. Самовывоз имеет доставку 0.

Для первой версии количество — целое число порций; произвольные весовые
значения и модификаторы не добавлять без расширения контракта.
Даты сохранять как UTC, в интерфейсе переводить в часовой пояс кафе.
В контракте использовать ISO 8601 с явным часовым поясом и отдельное поле зоны.

ID блюда не меняется вслед за названием. Внешний код блюда r_keeper хранится
в отдельном сопоставлении, если оно понадобится; нельзя вывести его из названия
или выдумать. Для тестового отправителя отсутствие такого кода допустимо.
Перед подключением r_keeper интегратор должен подтвердить сопоставление
всех доступных для заказа блюд и способ передачи стоимости доставки.

Версия заказа увеличивается при бизнес-изменении. Изменение статуса отправки
вебхука не изменяет принятую версию заказа. Событие содержит финальный снимок;
позднейшее изменение меню не переписывает его тело.

## 4. Предлагаемые API-маршруты

Названия уточняются при реализации, поведение обязательно. В API использовать
JSON; единый формат ошибки: `code`, понятное `message`, ошибки полей и
`requestId`. Ответы с заказами и сессиями — `Cache-Control: no-store`.

| Метод и маршрут | Назначение | Доступ |
| --- | --- | --- |
| `GET /api/menu` | Актуальные блюда и версия каталога | Публичный |
| `GET /api/order-settings` | Доступные получения, расписание, условия, слоты/ограничения | Публичный |
| `POST /api/order-quotes` | Проверка состава и расчёт | Публичный с ограничением частоты |
| `POST /api/orders` | Создание заявки по расчёту | Публичный с идемпотентностью и ограничением частоты |
| `POST /api/staff/session` | Обмен проверенного Telegram initData на сессию | Проверка Telegram и допуска |
| `POST /api/staff/orders/search` | Список, фильтры, поиск без телефона в URL | Сотрудник |
| `GET /api/staff/orders/{id}` | Карточка и история | Сотрудник |
| `POST /api/staff/orders/{id}/claim` | Взять свободный заказ | Сотрудник |
| `POST /api/staff/orders/{id}/release` | Вернуть в новые | Ответственный/руководитель |
| `POST /api/staff/orders/{id}/reassign` | Переназначить с причиной | Руководитель |
| `PATCH /api/staff/orders/{id}` | Сохранить согласуемые данные и пересчитать | Ответственный |
| `POST /api/staff/orders/{id}/contact-attempts` | Зафиксировать попытку звонка | Ответственный |
| `POST /api/staff/orders/{id}/accept` | Принять и создать событие | Ответственный |
| `POST /api/staff/orders/{id}/cancel` | Отменить до принятия | Ответственный; свободный заказ — руководитель |
| `POST /api/staff/events/{id}/retry` | Повтор существующего неудачного события | Руководитель |
| `POST /api/telegram/webhook` | Получение обновлений Telegram | Проверка служебного секрета Telegram |

Операции изменения принимают `expectedVersion`; устаревшая версия даёт `409`
с актуальной версией и предложением обновить карточку. Сервер проверяет
статус, роль, назначение и поля независимо от состояния кнопок интерфейса.

Для `POST /api/orders` и `/accept` обязателен `Idempotency-Key`.
Область ключа включает среду и операцию, для сотрудников — также пользователя.
Повтор идентичного запроса возвращает прежний результат; другое тело с тем же
ключом возвращает `409`. Повтор принятия уже принятого заказа возвращает
существующий результат и событие, если запрос не пытается изменить данные.

Для первоначального заказа хранить связь ключа с заказом весь срок хранения
заказа. Публичный повтор возвращает лишь минимальное подтверждение отправки,
не предоставляет доступ к другим заказам и истории сотрудников.

## 5. Создание заказа и Telegram-уведомлений

Сохранение заявки и записи о необходимости уведомить сотрудников выполнить
в одной транзакции. Сначала зафиксировать заказ, затем независимо отправлять
уведомления. Ошибка Telegram не означает потерю заказа и не заставляет гостя
заново оформлять его.

Базовый целевой срок появления уведомления при исправных внешних сервисах
и минутном cron — до 60 секунд. При необходимости более быстрой доставки
добавить немедленную обработку после фиксации с ограниченным временем,
оставляя cron для восстановления после сбоя.

Обработчик входящих Telegram updates проверяет секрет запроса и `update_id`,
быстро отвечает после надёжного сохранения/обработки. Команды выполняются
идемпотентно. Исходящие уведомления повторяются отдельно от вебхука интегратору.

## 6. Атомарное принятие и outbox

В одной SQL-транзакции:

1. Заблокировать запись заказа; проверить статус, ответственного и версию.
2. Проверить актуальные цены/доступность, телефон, получение, время и итог.
3. Зафиксировать окончательный снимок, `acceptedAt`, `acceptedBy`, статус `accepted`.
4. Добавить запись истории принятия.
5. Сформировать и сохранить неизменяемое событие `order.accepted` в outbox.
6. Записать необходимость обновить Telegram-уведомления.
7. Зафиксировать транзакцию, затем ответить Web App.

Если любой шаг записи не удался, принятие не фиксируется частично.
Нельзя получить «Принят» без сохранённого события. Сетевые обращения к Telegram
и интегратору выполняются после транзакции, не удерживая блокировки.

Уникальное ограничение на `(environment, order_id, event_type)` в первой версии
разрешает одно событие `order.accepted` для заказа. Несколько HTTP-попыток
доставки этого события ожидаемы и имеют один `eventId`.

Отправка имеет гарантию «как минимум один раз», а не обещание ровно одного
HTTP-запроса. Если получатель сохранил заказ, но ответ потерялся, запрос повторится.
Защита от второго заказа в r_keeper требует идемпотентного получателя.

## 7. Контракт события версии 1

Заголовки исходящего HTTPS POST:

```text
Content-Type: application/json; charset=utf-8
X-Delivery-Event-Id: <eventId>
X-Delivery-Timestamp: <Unix seconds of this attempt>
X-Delivery-Signature: v1=<hex HMAC-SHA256>
X-Delivery-Key-Id: <signing key identifier>
Idempotency-Key: <eventId>
```

Подпись: HMAC-SHA256 от строки `timestamp + "." + rawBody`, ключ — отдельный
секрет этой интеграции. `rawBody` — точные UTF-8 байты отправляемого JSON.
Получатель сравнивает подпись безопасным сравнением, проверяет допустимость
timestamp (начальное окно 5 минут) и сохраняет обработанный `eventId`.
При повторе тело и `eventId` прежние, timestamp и подпись для попытки новые.
Ключ интеграции отличается от токена бота и ключа входящего Telegram webhook.

## 8. Отправка, ответы и повторы

Адрес получателя и ключ задаются приватной серверной конфигурацией,
не поступают из браузера или тела заказа. Использовать HTTPS с проверкой
сертификата; не переходить автоматически по redirect. Разрешённый хост
зафиксировать конфигурацией, чтобы отправка не стала доступом к произвольным адресам.

Начальные параметры отправителя:

- Cron/worker запускается не реже раза в минуту.
- Соединение — до 3 секунд, общий запрос — до 10 секунд.
- Всего 8 автоматических попыток. После первой задержки: 1, 2, 10, 30,
  120, 360 и 720 минут; добавляется небольшой jitter.
- При `429` учитывать `Retry-After`, ограничив максимальную задержку настройкой.
- Сетевые ошибки, тайм-ауты, `408`, `425`, `429` и `5xx` повторять.
- Прочие `4xx` и `3xx` помечать как требующие исправления конфигурации/данных;
  не выполнять бесконечные автоматические повторы.
- После исчерпания попыток сохранить событие в состоянии `failed`,
  уведомить руководителя и разрешить ручной повтор того же события.

Любой `2xx` по договорённости означает, что получатель надёжно сохранил
событие и отвечает за его дальнейшую обработку. Опциональный ответ содержит
`eventId` и `receiptId`. Для повторного события получатель возвращает успешный
ответ о прежнем приёме, не создавая новый заказ. `409` не считать успехом
без отдельного согласования контракта.

Успешная доставка вебхука означает «Доставлено интегратору». Она не означает
«Создано в r_keeper». Для последнего нужен отдельный протокол подтверждения
с `orderId`, внешним номером и результатом. Такой протокол и его endpoint
проектируются вместе с интегратором на следующем этапе.

Состояния доставки: `waiting_configuration`, `pending`, `sending`,
`retry_scheduled`, `delivered`, `failed`. У заказа до принятия события нет.
При отсутствии адреса событие сохраняется в `waiting_configuration`,
а приложение показывает, что интеграция не подключена.

После подключения адреса накопленные события отправлять выбранным пакетом
под контролем руководителя с проверкой среды и актуальности, чтобы старые
тестовые/уже вручную обработанные заказы не оказались в рабочей кассе.

Worker берёт событие атомарно с ограниченной по времени арендой. Два worker
не должны одновременно владеть одной попыткой. После падения процесса
аренда истекает и событие возвращается в работу. Состояние не теряется
при публикации новой версии и перезапуске сервера.

## 9. Защита данных и публичный репозиторий

- В Git разрешены исходники, миграции, JSON Schema и вымышленные примеры.
- В Git и публичные артефакты не входят токены, `.env`, приватные конфиги,
  базы, резервные копии, реальные адреса/телефоны, payload рабочих заказов,
  сессии, Telegram initData, скриншоты реальных заказов.
- Секреты размещать в настройках сервера и защищённой среде GitHub Actions;
  не подставлять их в Vite-переменные, клиентский JavaScript и HTML.
- В CI не предоставлять deployment-секреты недоверенным pull request.
  Публикация выполняется из доверенной ветки/выбранного commit.
- Логи используют ID, статусы, длительность и маскированные ошибки;
  полные тела заказов/подписи не печатаются в публичные Actions-логи.
- Входные поля валидируются; вывод экранируется; SQL параметризован.
- Ограничить частоту создания расчётов/заказов и размер запросов.
  Дополнительную антибот-проверку подключать при необходимости, с серверной проверкой.
- CORS разрешает точные origins интерфейсов. Origin — это схема, хост и порт,
  а не путь репозитория Pages; разные пути одного origin не являются изоляцией.
  CORS не заменяет авторизацию сотрудника и проверку прав.
- Публичных endpoints перечисления заказов, проверки по телефону или доступа
  по одному последовательному номеру нет.
- Резервные копии базы защищены; восстановление проверяется до рабочего запуска.
  Срок хранения заказов и истории настраивается после согласования с владельцем.
- Использовать согласованные документы для оформления заказов, не копировать
  автоматически формулировки регистрации в клубе гостей как подходящие для доставки.

## 10. GitHub, стенд и комплект поставки

Не менять посторонние незавершённые работы в репозитории. Перед реализацией
зафиксировать состав нужных изменений и актуальное состояние меню/сборки.

Предлагаемые новые части проекта:

- `checkout.html`, `checkout.js`, `checkout.css`, модуль корзины.
- `staff.html`, `staff.js`, `staff.css` для Mini App.
- Серверные модули заказов, авторизации Telegram, уведомлений, outbox и отправителя
  в существующей структуре `hosting/php/`.
- Миграции SQL, приватные примеры конфигурации без секретов, команда cron.
- JSON Schema вебхука, контрактные фикстуры, инструкция интегратору.
- Расширенные сборки Vite/PHP; дополнительные страницы включаются в сборку,
  страницы сотрудников и тестовое окружение имеют `noindex`.
- GitHub Actions для проверок, сборки и публикации тестового окружения.

Изолировать `staging` и `production`: разные база, бот, ключи, адрес получателя
и конфигурация. Начальные данные меню для тестов брать из текущего сайта.
В публичном отчёте проверки указывать commit, URL стенда и обезличенные результаты.

Тестовый приёмник вебхука доступен по HTTPS, проверяет подпись, запоминает
`eventId` и позволяет воспроизводить успешный ответ, тайм-аут, `429` и `500`.
Его просмотр и управление сбоями защищены; публичного каталога payload нет.
Он не подключён к r_keeper и не выполняет реальные заказы.

## 11. Критические проверки серверной части

Автоматически в GitHub Actions и на опубликованном стенде проверить:

1. Создание заявки и задания уведомления происходит атомарно.
2. Принятие и создание события атомарны; ошибка записи откатывает оба.
3. Двойное принятие, параллельные запросы и повтор после потери ответа
   оставляют один принятый снимок и один `eventId`.
4. Цена берётся с сервера; сохранённая версия меню и сумма соответствуют
   согласованным данным, изменение меню не переписывает историю.
5. Web App сохраняет правки без события; событие появляется только при принятии.
6. Итоговый payload содержит все согласованные позиции, количества, суммы,
   телефон, получение, адрес и время; внутренние заметки отсутствуют.
7. HMAC соответствует точным байтам; подмена тела, неверный ключ и старый
   timestamp отклоняются тестовым получателем.
8. После тайм-аута с уже сохранённым на приёмнике событием повтор не создаёт дубль.
9. `500`, `429`, `401`, redirect и сетевой сбой дают предусмотренные состояния.
10. Падение worker и перезапуск сервера сохраняют очередь; параллельные worker
    и истечение аренды не теряют событие.
11. Отсутствующий адрес интегратора сохраняет событие без ложного успеха.
12. После `2xx` интерфейс не утверждает создание заказа в r_keeper.
13. Сбой Telegram не мешает сохранению и принятию; сообщение синхронизируется позднее.
14. Подмена сотрудника, ID заказа, роли, версии и недопустимый переход статуса запрещены.
15. Сборка и CI-артефакты не содержат секретов и реальных персональных данных.
16. Тестовые события технически изолированы от рабочего приёмника и бота.

## 12. Что передать и уточнить у интегратора

Передать документацию, JSON Schema, примеры доставки/самовывоза, правила HMAC,
повторов и идемпотентности, доступ к тестовому приёмнику/отправителю,
таблицу стабильных ID блюд и результаты сквозных проверок.

Получить адрес получателя, правила обмена секретом, подтверждение durable-приёма
и защиты от дублей, сопоставление блюд и доставки, требования к времени,
оплате и обязательным реквизитам, обработку ошибок кассы и способ сообщить
нашему приложению внешний номер заказа. Правки и отмены после принятия
согласовать отдельными событиями до добавления соответствующих кнопок.

Наша первая версия считается готовой, когда на опубликованном стенде
пройден маршрут от корзины до подтверждённого приёма события тестовым
интегратором, включая ошибки и повторы. Это не утверждение готовности
рабочего r_keeper или банковской оплаты.
