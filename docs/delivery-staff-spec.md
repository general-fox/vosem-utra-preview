# ТЗ: Telegram-бот и Web App сотрудников

Версия 1.0 от 28.09.2026. Рабочее задание для последующей реализации.

Связанные документы: [сайт и оформление](delivery-site-spec.md),
[сервер и вебхук](delivery-webhook-spec.md).

## 1. Назначение

Бот уведомляет о заявках с сайта и открывает приложение сотрудников.
Web App используется для звонка гостю, проверки состава и данных,
редактирования и принятия заказа. Сервер хранит данные и выполняет действия.
Сообщение Telegram отображает состояние заказа, но не является его хранилищем.

Основной сценарий: «Новый» → «Взять в работу» → звонок и правки
→ «Сохранить изменения» → «Принять заказ» → «Принят» и создание вебхука.
Если правки не нужны, после проверки можно сразу нажать «Принять заказ».

## 2. Сотрудники и права

| Роль | Права |
| --- | --- |
| Сотрудник | Смотреть заказы, брать свободные, изменять и принимать свои, отменять свои до принятия, отмечать звонки |
| Руководитель | Права сотрудника; переназначать заказы, отменять свободные заявки, повторять неудачную отправку вебхука |
| Администратор сайта | Управлять каталогом и допусками сотрудников через существующий защищённый административный контур |

Один человек может совмещать роли. Доступ к заказам не даёт автоматически
доступ к изменению меню, настройкам банка и секретам интеграции.

Допуск задаётся по постоянному Telegram user ID, с именем для интерфейса,
ролью и признаком активности. Telegram username и членство в группе не
используются как доказательство права доступа. Сотрудник не может добавить себя сам.
Для первой версии достаточно защищённого списка в серверной конфигурации
или существующей админке; отдельную большую систему управления персоналом не создавать.

Удаление допуска немедленно запрещает новые запросы API и уведомления этому
сотруднику. Заказы уволенного/отсутствующего сотрудника руководитель переназначает.

## 3. Авторизация Web App

При запуске Web App передаёт исходную строку `Telegram.WebApp.initData` серверу.
Сервер проверяет подпись и `auth_date`, получает Telegram user ID из проверенных
данных и сверяет его со списком сотрудников. Непроверенному `initDataUnsafe`
доверять нельзя. Источник:
[проверка данных Mini App](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

Начальное техническое правило: данные запуска принимаются не старше 5 минут,
допуск рассинхронизации часов — 30 секунд. Затем выдаётся короткая серверная
сессия сроком до 2 часов с повторной проверкой активности сотрудника в каждом запросе.
После истечения сессии предложить открыть приложение заново без потери
уже сохранённых правок.

При отдельном API использовать непрозрачный Bearer-токен в памяти приложения;
не передавать его в URL и не хранить в `localStorage`. Сессионное хранилище
содержит хеш токена. Если выбран cookie-вариант на одном origin, отдельно
реализовать CSRF-защиту и проверить работу cookie внутри Telegram.

Обычное открытие адреса в браузере без подтверждённой Telegram-сессии
не даёт доступа к заказам. Демонстрационные фикстуры допускаются только
в явно обозначенном тестовом интерфейсе, без подключения к рабочим данным.
Параметр ссылки с ID заказа определяет навигацию, но не предоставляет права.

## 4. Канал уведомлений и открытие приложения

Предлагаемый базовый вариант — личные сообщения бота допущенным сотрудникам.
Каждый сотрудник один раз запускает бота. Команды:

- `/start` — проверка допуска и инструкция по работе.
- `/orders` — кнопка открытия списка заказов.
- `/help` — краткое описание статусов и контакта ответственного.

Неавторизованному человеку бот отвечает «Доступ только для сотрудников»
без списка заказов и внутренних данных.

В личном чате уведомление содержит inline-кнопку `web_app` «Открыть заказ».
У Telegram этот тип кнопки доступен в личном чате пользователя с ботом.
Источник: [InlineKeyboardButton](https://core.telegram.org/bots/api#inlinekeyboardbutton).

Если заказчик выберет общую рабочую группу, использовать URL-кнопку с
прямой ссылкой на настроенную Mini App и параметром `startapp` с ID заказа.
Не пытаться поставить в группе личную кнопку `web_app`. Вход в группу
не отменяет серверную проверку сотрудника. Источник:
[прямые ссылки Mini App](https://core.telegram.org/bots/webapps#direct-link-mini-apps).

Точный режим рассылки выбирается конфигурацией. Для группы по умолчанию
показывать номер, сумму, получение, время и статус; контакт и адрес доступны
в авторизованной карточке. Для личных служебных уведомлений допускается
полная сводка ниже. Изменять уже опубликованные сообщения во всех выбранных
служебных чатах, сохраняя их `chat_id` и `message_id` на сервере.

## 5. Уведомление о новом заказе

В личном сообщении показать:

- Номер, дату создания и статус «Новый».
- Доставку или самовывоз.
- Желаемые дату/время либо «Как можно скорее».
- Имя, если указано, телефон, адрес доставки.
- Блюда, количество, суммы строк; сумму блюд, доставку и итог.
- Отдельную пометку, если стоимость доставки и итог ещё не определены.
- Комментарий гостя.
- Кнопку «Открыть заказ».

Длинные состав и комментарий сокращать в уведомлении до допустимого размера;
полные данные всегда доступны в Web App. Экранировать пользовательский текст,
чтобы он не менял форматирование сообщения или ссылок.

Нажатие «Открыть заказ» само по себе не принимает и не назначает заказ.
Номер последователен и удобен для разговора; внутренний ID непредсказуемый.

## 6. Список заказов в Web App

Основные разделы: «Новые», «На согласовании», «Принятые», «Отменённые».
Дополнительный фильтр «Мои», дата и поиск по номеру/телефону для сотрудников.
Список пагинированный; телефон и адрес не попадают в URL поиска или логи доступа.

В строке показывать номер, время поступления, получение, желаемое или
согласованное время, сумму, статус и ответственного. Заказы ко времени
должны заметно отличаться от заказов на ближайшее время.

Обновлять список при возврате в приложение и каждые 15 секунд, пока экран
активен. Показать время последнего обновления и кнопку ручного обновления.
Сбой сети не должен выглядеть как пустой список. Не включать сложные
WebSocket-зависимости ради первой версии.

## 7. Карточка заказа

Порядок блоков:

1. Номер, статус, ответственный и время создания.
2. Гость и кнопка «Позвонить» через `tel:`.
3. Способ получения, адрес и время.
4. Состав: названия, количество, цена, сумма строки.
5. Стоимость блюд, доставки и полный итог.
6. Комментарий гостя; отдельная служебная заметка сотрудника.
7. История изменений и попыток связаться.
8. Действия по текущему статусу.
9. После принятия — отдельный блок отправки интегратору.

В карточке всегда видны сохранённая версия и наличие несохранённых правок.
Обновление с сервера не затирает редактируемые поля без предупреждения.
При закрытии приложения с несохранёнными правками показать предупреждение,
если это поддерживается клиентом; дополнительно обозначить состояние формы.

## 8. Взять в работу и распределить

Кнопка «Взять в работу» атомарно переводит `new` в `processing` и записывает
ответственного. Если два сотрудника нажали одновременно, назначение получает
только один; второй видит актуальную карточку с именем ответственного.

Остальные могут просматривать заказ. Изменять, принимать и отменять его
может ответственный; руководитель сначала выполняет явное переназначение
с записью причины. Закрытие Web App не освобождает заказ автоматически.

Ответственный может явно «Вернуть в новые»; руководитель — переназначить
или вернуть в очередь. Состав и история при этом сохраняются.

После назначения уведомление меняется на «На согласовании · Имя сотрудника».
Изменение сообщения в Telegram не входит в транзакцию назначения:
если Telegram недоступен, состояние в базе всё равно остаётся правильным.

## 9. Редактирование при звонке

До принятия ответственный может:

- Удалить блюдо и изменить количество.
- Найти и добавить доступное блюдо из того же меню, что на сайте.
- Изменить телефон, имя, доставку/самовывоз и адрес.
- Уточнить желаемое и установить согласованное время.
- Указать стоимость доставки, если выбран режим ручного расчёта.
- Добавить служебную заметку и комментарий для выполнения заказа.

Создавать произвольные блюда, задавать произвольную цену блюда и скидку
внутри заказа нельзя. Новая позиция сначала создаётся через управление меню
с постоянным ID. Это необходимо и для последующего сопоставления с r_keeper.

Сумма пересчитывается сервером. В первой версии единое правило — при правке
состава и перед принятием использовать актуальные цены меню. Если цены
изменились относительно сохранённого заказа, показать разницу и потребовать
повторного согласования суммы; не повышать её незаметно.

Недоступное блюдо нельзя принять или заменить автоматически. Сотрудник
согласует удаление/замену с гостем. Если блюдо снова доступно, уполномоченный
администратор меняет доступность в общем меню.

Переключение на самовывоз убирает адрес из актуальных данных и обнуляет доставку;
исходные данные остаются в истории. Переключение на доставку требует адрес
и определённую стоимость до принятия.

## 10. Сохранение, контакт, отмена

«Сохранить изменения» записывает новую версию заказа, автора, время и разницу.
Статус остаётся `processing`; вебхук `order.accepted` не создаётся.

«Не дозвонились» записывает время попытки и необязательный комментарий;
заказ остаётся на согласовании. Можно указать время повторного звонка
как заметку; автоматический обзвон и отдельные напоминания не входят в первую версию.

«Отменить заказ» доступно до принятия. Требуются причина и подтверждение действия.
Причины: отказ гостя, нет доступных блюд, невозможно доставить, дубль, другое.
Для «Другое» требуется текст. Дубликат по возможности связывается с основным заказом.
Отмена сохраняется, уведомление обновляется, вебхук принятия не создаётся.

## 11. Принятие заказа

Перед принятием должны выполняться все условия:

- Заказ на согласовании и назначен текущему сотруднику.
- Нет несохранённых изменений и конфликта версии.
- Состав непустой; блюда доступны, количества и актуальные цены проверены.
- Есть корректный телефон и адрес для доставки.
- Установлено конкретное согласованное время получения/доставки,
  включая заказ, первоначально оформленный «как можно скорее».
- Стоимость доставки известна; итог рассчитан сервером.
- Сотрудник явно подтвердил: «Связался с гостем, состав, сумма и время согласованы».

Кнопка «Принять заказ» вызывает серверный endpoint с ожидаемой версией
и ключом идемпотентности. Сервер за одну транзакцию сохраняет статус `accepted`,
финальный снимок, автора принятия и исходящее событие. Затем возвращает результат.
Механизм описан в ТЗ вебхука.

Отключение кнопки в интерфейсе дополняется серверной защитой от повторов.
Закрытие приложения или потеря ответа не создают второй заказ/вебхук:
после повторного открытия загрузить уже сохранённый результат.

После успеха уведомление содержит статус «Принят», актуальный состав,
сумму, время, сотрудника и кнопку «Просмотреть заказ».

## 12. После принятия и статус интеграции

В первой версии принятый заказ доступен для просмотра. Его финальный снимок
не редактируется и не удаляется. Это начальное ограничение версии, а не
согласованное с заказчиком постоянное правило.

Если гость просит изменить или отменить уже принятое, сотрудник видит
инструкцию обратиться к ответственному за кассу. До согласования протокола
корректировки с интегратором нельзя локально менять статус на «Отменён»
и создавать ложное впечатление, что отмена дошла до r_keeper.
Позже изменения потребуют отдельных версий и событий, а не повторного `order.accepted`.

Отдельный блок интеграции показывает:

| Состояние | Текст сотруднику |
| --- | --- |
| Нет настроенного получателя | «Заказ принят. Ожидает подключения интеграции» |
| В очереди / отправляется | «Заказ принят. Передача ожидается / выполняется» |
| Запланирован повтор | «Заказ принят. Повтор передачи запланирован» |
| Ошибка | «Заказ принят. Не удалось передать — требуется внимание» |
| Получатель подтвердил HTTP-приём | «Данные доставлены интегратору» |

HTTP-успех нашего вебхука не доказывает создание заказа в r_keeper.
«Создан в r_keeper» можно показывать только после отдельного согласованного
подтверждения интегратора с внешним номером. До этого поле состояния кассы —
«Не подключено» или «Нет подтверждения».

Руководителю доступна повторная отправка существующего неудачного события.
Она не возвращает заказ в `processing`, не принимает его заново и не создаёт
новый ID события. Обычному сотруднику технические секреты и тело подписи не показывать.

## 13. Надёжность и удобство

- Хранить связь заказа с каждым уведомлением. Обновление сообщения выводит
  актуальное состояние из базы, а не пересылает устаревший текст из очереди.
- Сбои Telegram повторять с учётом ограничений API. При удалённом сообщении
  допускается новое уведомление со ссылкой на тот же заказ.
- Неудачная доставка уведомления не удаляет заказ и не откатывает принятие.
- О повторяющемся сбое показывать руководителю запись в Web App;
  не полагаться только на тот же недоступный Telegram-канал.
- Интерфейс адаптируется к теме и размерам Telegram, безопасным отступам,
  экранной клавиатуре и возврату из фона.
- При потере сети изменения не изображаются сохранёнными. Показывать понятную
  ошибку, возможность повтора и время последней синхронизации.
- Служебные комментарии не должны автоматически попадать гостю или интегратору.

## 14. Проверки бота и Web App

На опубликованном HTTPS-стенде, в Telegram на Android, iPhone и компьютере:

1. Допущенный сотрудник открывает карточку из уведомления; посторонний получает отказ.
2. Подделанные/просроченные данные Telegram и отозванный доступ отклоняются API.
3. Кнопка из личного чата работает; групповой вариант проверяется отдельно,
   если выбран заказчиком.
4. Одновременное назначение имеет одного победителя; второй сотрудник не теряет контекст.
5. Правки сохраняются с автором, временем и новой версией; конфликт не затирает чужую работу.
6. Добавление и удаление блюд, количества, получение, адрес и доставка пересчитывают итог.
7. Кнопка сохранения не создаёт событие принятия.
8. Пустой состав, неизвестная доставка, несогласованное время и недоступные блюда
   не позволяют принять заказ.
9. Двойное принятие, повтор после тайм-аута и две открытые карточки создают один результат.
10. После принятия сообщение обновляется, карточка доступна для просмотра,
    снимок и событие совпадают по составу, адресу, времени и сумме.
11. Недозвон и отмена до принятия не отправляют вебхук принятия.
12. Сбой Telegram не мешает работе со списком; сбой интегратора виден отдельно
    и не выдаётся за непринятый заказ.
13. Нет обрезанных действий, перекрытия клавиатурой и несохранённых правок,
    которые выглядят как сохранённые.
