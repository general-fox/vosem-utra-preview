# Подготовка переноса на vosem-utra.ru

Эти инструкции не выполняют публикацию. Порядок работы: локальная проверка,
согласование через отдельный GitHub-предпросмотр, затем перенос на основной домен.
Секреты и рабочее хранилище не входят в публичный репозиторий.

**Для вашего хостинга используйте [PHP-сборку и инструкцию REG.RU](reg-upload.md):
`npm run build:reg`.** Ниже сохранены результаты разбора прежнего архива и
требования исходного Node-варианта; они не являются инструкцией запуска PHP.

## Требования к хостингу

### Что известно из последней размещённой сборки

28 сентября 2026 года проверены два предоставленных владельцем архива:
`vosem-utra-reg-ru-2026-09-21-cookies-style.zip` и
`vosem-utra-redirect-fix-2026-09-21.zip`. Архивы прочитаны без выполнения
PHP, загрузки на сервер или копирования приватных настроек в репозиторий.

Это статические страницы с PHP-обработчиком регистрации `site/api/register.php`
и правилами Apache `.htaccess`. Инструкция внутри полной сборки рассчитана на
PHP 8.3/8.4, cURL и сессии; это требования сборки, а не подтверждение версии PHP
на действующем сервере. Название тарифа и возможность постоянно запускать Node.js
из этих файлов установить нельзя.

Исправление из второго архива удаляет перенаправления HTTPS и `www` из корневого
`.htaccess`: ими управляет хостинг. При подготовке совместимой PHP-сборки нужно
сохранить этот вариант, включая запрет доступа к служебным файлам, и не возвращать
дублирующие правила из первого архива. Сам факт наличия исправления не подтверждает
текущие настройки перенаправлений или TLS на сервере.

В полной сборке также есть форма клуба гостей, PHP-интеграция, cookie-интерфейс,
юридические страницы и приватные настройки. Текущий `dist-hosting` не заменяет
этот комплект: форма клуба в репозитории демонстрационная. Перед реальным
обновлением нужно сохранить действующую регистрацию, согласованные версии
документов и накопленные записи согласий; нельзя заменять их демонстрационной
формой или старыми файлами из архива без сверки.

Форма обращается к PHP API и загружает reCAPTCHA с `www.recaptcha.net`.
Текущий Node-сервер не исполняет PHP, а его CSP допускает скрипты только
с собственного домена и с nonce. Копирования файлов формы недостаточно:
потребуются корректная маршрутизация в PHP и отдельная проверка CSP для
регистрации, без ослабления защиты админки.

Полный архив содержит приватные конфигурационные файлы интеграций. Его нельзя
добавлять в публичный GitHub. Рабочий `vosem-utra-private` и записи согласий
должны оставаться вне публичного каталога и сохраняться при обновлении.

Первоначальная серверная часть админки написана на Node.js. Для прежней схемы
размещения добавлен отдельный PHP runtime в `hosting/php`: API меню, MFA,
загрузка фото и актуальный HTML/SEO. Он включается командой `npm run build:reg`.
Сам по себе `dist-hosting` остаётся сборкой для Node, а не PHP-комплектом.

### Требования текущей реализации на Node.js

Текущая админ-панель работает с Node.js 24+, одним постоянно работающим процессом
и постоянным доступным для записи каталогом `.data/`. Нужны HTTPS reverse proxy
и возможность хранить `.env` вне публичного каталога. В REG.RU уточните точный
тип услуги и тариф: инструкция для VPS не означает наличие такого окружения
на обычном виртуальном хостинге.

[REG.RU: Node.js и Nginx на VPS](https://help.reg.ru/support/servery-vps/oblachnyye-servery/ustanovka-programmnogo-obespecheniya/deploy-react-prilozheniya).
Если тариф предоставляет только PHP, этот backend на нём не запускается:
понадобится адаптация backend под PHP либо подходящая серверная услуга.
Одной загрузки папки сборки достаточно для статической витрины, но не для
работающей админ-панели и обновления её меню.

## Подготовка production на сервере

1. Разместите проект вне document root веб-сервера. Не отдавайте весь репозиторий
   через Nginx/Apache. Установите зависимости `npm ci`.
2. Создайте приватный `.env` по `.env.example`: `NODE_ENV=production`,
   `PUBLIC_ORIGIN=https://vosem-utra.ru`, `HOST=127.0.0.1`, `PORT=3000`.
3. Создайте случайный `AUTH_ENCRYPTION_KEY` командой из `.env.example`, сохраните
   его в `.env` и отдельно в менеджере паролей. Не вставляйте ключ в чат или Git.
4. На новом сервере без аккаунта задайте в приватном окружении
   `ADMIN_USERNAME=v.utra@yandex.ru` и случайный `ADMIN_PASSWORD` от 15 символов.
   Это первоначальный доступ для владельца, а не общедоступная регистрация.
   Если переносите существующий аккаунт, сохраните его `.data` и тот же ключ
   шифрования; смена ключа без повторной настройки сделает MFA недоступным.
5. При наличии добавьте публичные токены `GOOGLE_SITE_VERIFICATION` и
   `YANDEX_VERIFICATION` (значения метатегов из кабинетов вебмастеров).
6. Выполните `npm test`, `npm run build:hosting`, затем `npm start`.
   Автоматический перезапуск процесса настройте средствами хостинга.
7. Настройте HTTPS reverse proxy на `127.0.0.1:3000` для **всех** запросов.
   Главная отдаётся Node-сервером: так цены, скрытие блюд и JSON-LD остаются
   актуальными без пересборки. Прокси должен сохранять исходные Host и Origin,
   не кэшировать `/api/`, `/admin.html` и HTML главной. Ограничьте тело запроса
   примерно 6 МБ, чтобы загрузки до 5 МБ проходили. Внешний доступ к порту 3000
   закройте; порт предназначен только для локального прокси.
8. На уровне хостинга перенаправьте HTTP и при наличии `www` на
   `https://vosem-utra.ru`. TLS-сертификат должен покрывать адреса перенаправления.
   Backend не доверяет присланным посетителем X-Forwarded-* заголовкам.
9. Владелец входит на `/admin.html` с первоначальной почтой и паролем. Панель
   показывает подключение Яндекс ID (Ключ): сканирование QR, подтверждение кода
   и сохранение резервных кодов. Доступ к меню появляется после подтверждения.
   После успешного подключения удалите `ADMIN_PASSWORD` из окружения: файл
   аккаунта уже имеет приоритет. Для обычных входов команды сервера не нужны.

Node добавляет CSP с отдельным nonce на каждый HTML-ответ, запрет встраивания,
nosniff и HSTS при настроенном HTTPS origin. Прокси не должен заменять эти
заголовки или кэшировать HTML с nonce. CSP разрешает встроенные стили,
используемые дизайном и анимациями; скрипты разрешены с собственного домена
и с серверным nonce. Встроенная форма клуба остаётся демонстрационной.

## Сохранность данных и обновления

Перед заменой кода сохраните защищённую резервную копию `.data/` и отдельно
ключ шифрования из `.env`. Проверьте восстановление на непубличной копии.
Данные и секреты не размещайте в `dist`, `dist-hosting`, `public` или `assets`.
Обновление сборки не должно удалять `.data/`; seed-меню используется только
если сохранённого меню ещё нет. Аудит хранится в `.data/security-audit.jsonl`
с ограниченным размером и одной резервной ротацией; доступ только оператору.

Перед публикацией проверяются вход с MFA и резервным кодом, добавление/скрытие
блюда, загрузка фото, выход, отсутствие секретов по HTTP, реальные HTTPS/cookie
и robots/sitemap. После публикации нужно проверить фактические ответы домена:
локальные тесты не проверяют настройки REG.RU. Подключение поисковых сервисов
описано в [SEO](seo.md).

## Предпросмотр

`npm run build` → `dist` сохраняет `noindex` на всех страницах. Этот каталог
подходит для статического просмотра; API и вход на GitHub Pages отсутствуют.
Текущий вариант Pages из корня репозитория также сохраняет `noindex` и читает
начальное меню из `public/data/menu.json`. Публичный репозиторий и `noindex`
не ограничивают доступ к исходникам: перед push проверьте состав изменений.
